# 讨论与决策记录

本文是字幕组在线工作台需求讨论的精简版，只保留原始诉求、每轮决策与理由。完整对话（含命令输出和各版文档全文）见 [archive/讨论文档.原始对话记录.md](archive/讨论文档.原始对话记录.md)。当前有效的设计以《[产品设计文档](字幕组在线工作台-产品设计文档.md)》为准。

## 1. 原始诉求

> 我们目前的工作表是一个共享文档，在本文件夹的xlsx中，txt文件是群文件的文件树，我们字幕组目前有下面的诉求：
> 1、纯靠q群群文件上传工作内容，太乱太杂了，而且有些东西还会有很多个版本要保存，鱼龙混杂
> 2、有些大文件还没发直接传q群，需要靠各种网盘
> 3、在工作表看了进度后，还要去群文件翻对应的文件在哪里
> 所以我想做一个在线的、直接挂载文件到具体任务上的工作表，文件支持用户自己上传，都弄到cf r2上去，也支持填写网盘链接，各种网盘都行，一个或者多个网盘都行。

## 3. 用户确认的范围决定

第 2 轮的五点修正是产品范围的硬约束，不再作为待选方案：

1. **版本更新不需要审核。** 能保存历史文件、显示版本历史即可。
2. **不做“版本”与“采用”的解耦。** 各环节工作必然存在时间差，默认展示最新版本。
3. **长视频切块分工不由系统做。** 沿用原工作表的形式；小幅修改群里会沟通。
4. **不需要截止日期。**
5. **不需要讨论与交接记录。**

由此从设计中删除：审核/待审/退回流程、当前采用版本、输入版本追踪、上游变更提示、发布快照、分段对象与区间校验、依赖与合稿管理、计划日期与逾期提醒、评论区与活动流。

## 4. 选型决策与理由

### 4.1 自建，不魔改现有产品

| 方案 | 优点 | 代价 | 判断 |
|---|---|---|---|
| 魔改 Baserow 等 | 立即得到表格、筛选、字段、协作基础 | 文件版本、多网盘入口、任务侧栏仍要定制；深改核心增加升级成本 | 仅作对照 |
| Baserow 插件扩展 | 少改核心 | 官方称插件仍属实验阶段，API 标为 `0.0.1-alpha` | 不适合长期依赖 |
| **组件自建** | 数据模型与操作流程完全按实际用法设计 | 自行实现登录权限、表格读写、导入导出、备份 | **采用** |

理由：范围简化后，通用平台的大量能力用不上却仍要部署和维护，而真正需要的文件版本与任务关联反而要自己扩展。

### 4.2 界面库：shadcn/ui

| 选项 | 定位 | 判断 |
|---|---|---|
| **shadcn/ui** | 源码放进自己仓库、可自由修改的组件 | **采用**。侧栏、选择器、弹层都要按业务定制信息密度与布局 |
| Radix Primitives | 无样式的底层交互组件 | 不单独使用；选 shadcn/ui 的 Radix 版本即已包含 |
| HeroUI | 带默认视觉风格的组件库 | 可行但定制空间较小；当时处于 v2 到 v3 的 API 迁移期 |

代价：修改过的组件由自己维护，上游更新需自行评估合并。

### 4.3 表格：TanStack Table，不用 Glide Data Grid

用户要求“更现代、符合操作逻辑、逻辑不复杂、更直观”。

| 比较项 | TanStack Table | Glide Data Grid |
|---|---|---|
| 定位 | 只提供表格逻辑，界面自由组合 | 完整度高的可编辑网格 |
| 人员 + 状态合并显示 | 容易 | 需遵循其渲染与编辑接口 |
| 文件入口作为明显的操作 | 容易 | 需自定义单元格 |
| 大片连续编辑、框选、粘贴 | 需自己组合 | 现成 |
| 手机上换成卡片布局 | 方便 | 网格本身不解决 |

理由：主要操作是看分工、改进度、取文件、传文件，而非 Excel 式的批量填格。TanStack 自身不提供外观，直观与否取决于界面设计。

**重新评估的条件**：如果试用后发现成员高频依赖“从 Excel 粘贴一片、方向键连续填写、框选批量改值”，再考虑把核心表格换成 Glide，周边仍用 shadcn/ui。

由此确定的交互方式：

- 工序格合并显示“负责人 · 状态”，点击弹出小面板修改。
- 文件列直接显示“字幕 v3 · 4 个文件”这类可识别信息，点击打开右侧文件栏。
- 文件栏中最新文件在前，直接下载、打开网盘、上传新版；历史版本折叠。
- 标题与分工说明点击即改；“全部 / 我的任务 / 进行中”快捷筛选。
- 多网盘、提取码、旧版本等复杂信息进入文件栏后再展开，主表只关注分工与进度。

### 4.4 开发顺序

按业务闭环拆模块，每个模块同时包含前端、接口、数据与验收，不分“先前端后后端”。顺序：技术验证（表格与 R2 上传）→ 权限 → 工作表 → 任务文件与网盘入口 → R2 上传与版本历史 → 旧资料导入 → 运维与试运行。

首个里程碑：登录 → 打开工作表 → 改负责人或状态 → 打开任务文件 → 上传到 R2 → 看到新版本 → 下载旧版本。

### 4.5 阶段 0 之后

技术路线验证可行，阶段 0 结项。用户明确：**不以原型源码为开发基础**，正式产品从阶段 1 新建工程；20 GiB 上限与成员真实网络的验证转入阶段 4/6。

### 4.6 实时协同：服务端权威 + 事件广播

v1.5 曾建议“不做实时协同，约 30 秒刷新一次”，用户否决，要求做实时协同并参照开源项目。阅读克隆下来的源码后，发现三种做法：

| 做法 | 代表 | 判断 |
|---|---|---|
| **写入走普通接口，事务提交后向订阅者广播事件；事件带编号，重连按游标补发** | Baserow | **采用** |
| 操作变换（OT）：每条记录是带版本的文档，变更是操作 | Teable（ShareDB） | 模型更重、强依赖 Redis，其并发合并能力用不上 |
| CRDT：客户端合并文档状态 | Plane（Yjs + Hocuspocus，仅页面富文本） | 适合长文本；会让数据库不再是唯一事实来源 |

NocoDB 社区版的 socket 只做遥测，Vikunja 没有实时通道。

理由：格子里都是短文本、人员和状态，字段级“后写生效”加上“能看见谁正在编辑哪一格”就够了；权限、搜索、导入、版本事务都依赖关系数据库作为唯一事实来源。

包含：他人修改即时可见、在线成员、他人选中与正在编辑的格子、断线重连自动补齐。**不包含**：同一个格子里两人同时打字的字符级合并。

带来的约束：后端必须支持 WebSocket 长连接；阶段 0 没有验证过实时通道，阶段 1 需先做最小验证。

### 4.7 后端与部署：VPS 上的单个 Node 进程

用户确认登录用邀请链接注册加用户名密码，成员可编辑所有任务行、删除进回收站；后端与数据库委托选型，部署在 VPS 或 Cloudflare 均可。

选定：TypeScript 前后端同语言，Node.js + Fastify，同进程 WebSocket，PostgreSQL，Docker Compose 部署在一台 VPS 上；文件仍放 R2。

- **选 VPS 而非 Cloudflare Workers**：Workers 上长连接要 Durable Objects、数据库要 D1 或外接、后台作业要 Cron 与 Queues，每一项都是平台专有做法；小组自用的工具用单进程更简单，也更容易排查。
- **选 PostgreSQL 而非 SQLite**：并发上传时的版本号分配与额度结算需要行级锁。
- **选 Fastify**：阶段 0 已用它跑通上传签名与完成校验链路。
- **不引入 Redis**：单实例下事件在进程内分发，后台作业用基于 PostgreSQL 的队列。

### 4.8 首页看板、存储管理与若干参数

用户提出：

- **首页是任务流转看板**，并显示当前用户认领的进行中任务。看板上的任务带标签：任务类型、还有哪些职位没人填。大任务可折叠展开看小任务，大任务显示小任务标签的并集。
- **不设成员额度和项目总额度**，只给管理员看占用统计；另做一个管理员页面，能快速浏览占用、快捷选择并清理。
- **单文件上限 10g**；**大视频历史版本全部保留**。
- **实时事件保留时长**委托决定。
- **手机端**：查看与轻量编辑，可以做上传；既然都是浏览器，和网页端一样也行。

落实方式：

- 看板按工序分列，只有四列：时轴 → 翻译 → 校对 → 嵌字（用户确认）。最初提议的“待开始 / 进行中 / 待发布 / 已发布”被否决；后来提议的“待发布”列和其他工序的归属配置也被否决——其他工序暂不上看板。
- 工序不能写死（用户指出：不是所有任务都有校对环节）。看板列做成项目级配置，初始为上述四列；任务有哪些工序由其工作表的工序列决定，没有的工序不参与任何判断。
- 并行工序的任务在多列同时显示（用户确认）：时轴列显示任务 1 进行中，翻译列也显示任务 1 进行中。
- 看板只显示小任务，大任务作为小任务卡片上的标签（用户确认）。用户最初设想的“大任务可折叠展开、显示并集标签”由用户自己改为此方案。
- 大任务定义为同一工作表内“所属作品”相同的行（用户确认），“所属作品”改为选择或新建，避免写法不同被拆开。
- 类型标签取工作表名；缺人标签是未完成且无负责人的适用工序，点击即认领。卡片位置由工序状态推导，不可拖动。
- 尚待确认：还没人开始的任务放在第一个未完成工序的列；不上看板的工序缺人时仍显示缺人标签。
- 额度相关的预留、结算、对账全部删除；管理员存储页提供统计、按条件快捷选择（非最新版本、已发布任务的旧版本、超过若干天、大于某大小、回收站、未完成上传）与清理，默认移入回收站，最新版本不可批量删除。
- 实时事件保留 24 小时。
- 手机与桌面功能一致，只是布局不同。

向用户解释、尚待其决定的三件事：是否需要“参考资料”页；只有网盘链接的资源在内容更新时是否记为新一版；文件是否另存备份（默认只备份小文件）。

### 4.9 阶段 1 开工前的确认

写《[阶段 1 开发文档](阶段1-开发文档.md)》时分四轮向用户确认，结论如下。

| 事项 | 结论 | 来源 |
|---|---|---|
| 文档读者 | AI 编码代理，按任务逐个实现 | 用户选择 |
| 代码位置与托管 | 本目录建工程，GitHub 私有仓库 `1zero224/nameless-worksheet`，GitHub Actions 做 CI | 用户选择 |

| 首个管理员 | 在服务器上执行初始化命令创建 | 用户选择 |

| 邀请链接 | 可配置，默认 7 天、单次、普通用户 | 用户选择 |
| **角色** | **只有管理员和普通用户**，取消“统筹”；原统筹的权限（建表、配置列、看板列、导入导出）全部归管理员，管理员可有多个 | 用户决定，改动了 v1.8 的三角色权限表 |
| **停用账号** | **暂不做**，也不做“停用后断开实时连接”；要让某人无法再进入时由管理员重置其密码 | 用户决定，改动了 v1.8 的 A21 |

说明：用户对“停用后断开”的回答是“不做停用后被断开”。“会话失效（登出、密码被重置或修改）时断开实时连接”仍保留在阶段 1，因为它是“重置密码以阻止某人进入”这一替代办法能生效的前提；这一点是 AI 的理解，未经用户逐字确认。

### 4.10 阶段 2 开工前的确认

写《[阶段 2 开发文档](阶段2-开发文档.md)》前通过两轮结构化访谈确认了以下关键决定：

- **工作表与看板列结构配置对全体用户开放**（[ADR-0003](adr/0003-open-worksheet-structure-to-all-users.md)）：不再拆为“管理员管结构 + 个人本地存列宽/显隐”，所有用户均可建表、配列、调列宽与显隐、改看板列，直接落库实时同步；仅临时筛选与排序留在当前浏览器页面。
- **取消归档页与独立回收站，改用修改记录兜底**（[ADR-0004](adr/0004-change-log-replaces-recycle-bin.md)）：移除左侧导航的“归档”；工作表与任务详情侧栏提供永久保留的字段级修改记录，删除任务保留完整快照并在删除记录旁提供一键恢复。
- **已发布行默认折叠在工作表顶部**：类似 todolist 可展开回顾与编辑；所有工序已完成但未发布的行暂不折叠。
- **同表工序列与看板列 1:1 映射**：初校/终校等特例直接写进工序备注，不建多对一映射。
- **确认两条看板默认值与认领规则**：未开始任务落首个未完成上看板适用工序列；不上看板工序缺人也出缺人标签；点击缺人标签认领只填负责人、保持“未开始”，并发抢认领时后到者提示失败；已发布任务直接离开看板。
- **阶段 2 同步上线检索页与任务详情侧栏**：`/search` 先搜任务各字段，阶段 3 再扩文件；任务详情侧栏文件区先占位；负责人阶段 2 即支持项目用户与纯文本名字并存。
- **术语收敛**：工作表去掉冗余的“分类”字段改为标签颜色；[GLOSSARY.md](../GLOSSARY.md) 统一收录工作表、作品、任务、看板列、工序列、工序格、负责人、修改记录、在线状态。

### 4.11 UI 形态纠偏与 Teable 级多维表格重构（v1.11）

阶段 2 交付并部署试玩后，用户对照原工作簿 `无名字幕组任务分划.xlsx` 与 Teable / NocoDB / Grist / Glide Data Grid 等同类方案，指出三处形态偏移并拍板纠偏（详见 [ADR-0005](adr/0005-teable-grid-and-unified-attachment-slots.md) 与 [Teable级UI重构-实验设计文档.md](Teable级UI重构-实验设计文档.md)）：

- **坚守核心业务底线，拒绝原版替代与全栈魔改**：用户明确无法接受无同名文件自动版本堆叠，也无法接受看板不支持同一任务并行出现在两列；同时实查 Teable 全仓达 8,361 文件且运行需 4 GB+ 内存（现有香港 VPS 仅 3.8 GB），且其 S3 仅支持单次 PUT（无 10 GiB 分片续传），故保留本项目轻量后端与实时协同。
- **仅抽离 MIT 许可的 Teable Canvas Grid 核心**：经用户明确批准，放行按 MIT 协议将 `research/teable/packages/sdk/src/components/grid/`（91 文件）精简去耦至 `apps/web/src/vendor/teable-grid/`（保留 MIT 版权声明，不引入 Teable 品牌资产，不拷贝 `apps/` 下 AGPL 代码），外围界面切向 Teable 同源的 `shadcn/ui` 极简半透明灰阶 Token + `tw-animate-css` + `motion` + `sonner`，并补齐极简侧边栏与工作表顶部「表格视图 / 看板视图」标签栏。
- **作品大标题横幅 + 看板列内作品聚合**：工作表中不再每行重复显示「作品」列，改为类似原 Excel 的跨整行可折叠「作品大标题横幅」（无作品的独立任务直接平铺）；看板上将同列内归属同一作品的分段合并为默认折叠的「作品聚合卡」，支持看板列竖向折叠与卡片去噪，彻底消除长视频分段刷屏。
- **四级统一附件挂载（直通作品大标题与工序格）**：阶段 3 的 `artifacts` 统一覆盖项目参考资料、作品大标题共用附件（整片原片/字体包/合稿成品）、任务行通用附件、以及工序格交付附件（整格状态色 + 格内角标一键下载最新版），让单道工序在格子内一步走完。

## 6. 讨论未覆盖、已在设计文档中补充的问题

以下问题在讨论中没有被提出，设计文档给出了默认做法并标注“建议默认”，需要用户确认（详见设计文档第 14.1 节）：

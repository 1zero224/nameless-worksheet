## 1. 目标与退出条件

阶段 1 交付一个可部署的空壳：能登录、能邀请人、权限与项目隔离机制就位、实时通道骨架经过验证。不包含任何工作表、任务、文件功能。

退出条件（全部满足才算完成，逐条对应第 13 节的验收清单）：

1. 用户可通过邀请链接注册并登录，进入项目后看到完整导航。
2. 未登录者无法访问任何数据接口，也无法建立实时连接。
3. 一个项目的用户通过 API、对象 ID 或实时订阅都访问不到另一个项目的数据。阶段 1 还没有任务和文件，这一条由项目范围校验的公共机制与自动化测试保证，后续阶段新增的每个接口沿用同一机制。
4. 普通用户调用任何管理接口都被拒绝。
5. 两个浏览器之间能收到对方触发的测试事件；断线重连后自动补齐错过的事件；超出补发能力时收到“整体刷新”指令。
6. 会话失效（登出、密码被重置或修改）后，其实时连接立即被断开。
7. CI 在 GitHub 上通过；镜像可在 VPS 上拉取运行，经临时域名以 HTTPS 访问，健康检查正常。

### 5.2 字段规则

规则定义在 `packages/shared`，前后端共用同一份 Zod 定义。

| 字段 | 规则 |
|---|---|
| 登录名 | 匹配 `^[a-z0-9_]{3,32}$`；输入先转小写再校验；注册后不可改 |
| 显示名 | 先做 Unicode NFC 归一化并去掉首尾空白；1–32 个字符；不含控制字符；全局唯一 |
| 密码 | 8–128 个字符；转小写后不得等于登录名；不要求复杂度 |
| 邀请有效期 | 1、7 或 30 天，默认 7 |
| 邀请可用次数 | 1–50，默认 1 |
| 邀请角色 | `admin` 或 `user`，默认 `user` |

### 5.3 不变量

1. 每个项目始终至少有一个管理员。调整角色时在事务里用 `SELECT … FOR UPDATE` 锁住该项目全部管理员的 membership 行，确认降级后仍有管理员，否则拒绝。两个管理员同时互相降级不能把项目降到零管理员。
2. 邀请的使用是原子的：用一条带条件的 `UPDATE … SET used_count = used_count + 1 WHERE used_count < max_uses AND revoked_at IS NULL AND expires_at > now() RETURNING` 抢名额，更新不到行即视为邀请无效。并发注册不会超用。
3. 令牌（会话、邀请、重置）都是 32 字节随机数的 base64url 形式，数据库只存其 SHA-256。
4. 同一用户同时只有一个有效的重置链接：生成新的时把旧的未使用记录标为已使用。

| `migrate` | 执行未应用的迁移 |
| `init --project <名称> --admin <登录名> --display-name <显示名>` | 仅当数据库里没有任何项目时可用。创建项目、无密码的首个管理员，并输出一条 24 小时有效的重置链接。已初始化时报错退出，不做任何修改 |
| `reset-link <登录名>` | 为指定用户生成重置链接。用于唯一的管理员忘记密码等情况 |

首个管理员的密码由本人打开重置链接后在浏览器里设置，命令行和代理都不接触密码。网页上不存在任何免邀请的注册入口。

### 6.2 密码

Argon2id，参数 `memoryCost=19456`（KiB）、`timeCost=2`、`parallelism=1`。参数集中定义为常量；校验密码后若发现哈希参数与当前常量不同，顺手重新哈希。登录时不论登录名是否存在都执行一次哈希计算，避免通过响应时间探测登录名；登录名不存在和密码错误返回完全相同的错误。

### 6.3 会话

- Cookie 名 `nw_session`，值为会话令牌；属性 `HttpOnly`、`SameSite=Lax`、`Path=/`，生产环境加 `Secure`。
- 有效期 30 天，滑动续期：鉴权时若距 `last_seen_at` 超过 24 小时，则更新 `last_seen_at`、把 `expires_at` 顺延到 30 天后并重发 Cookie。
- 允许多设备同时登录，每台设备一个会话。
- 登出：删除当前会话。
- 自己修改密码：删除该用户**除当前会话外**的全部会话。
- 用重置链接设置新密码：删除该用户的**全部**会话。
- 管理员为某用户生成重置链接：立即把该用户的 `password_hash` 置空并删除其全部会话。这使“重置但不给链接”可以作为阻止某人进入的手段（见第 2.2 节）。
- 任何删除会话的操作，在事务提交后都要通知实时通道断开这些会话上的连接（第 8.6 节）。
- 后台作业每小时清理过期的会话、邀请与重置记录。

### 6.4 跨站请求防护

不使用单独的 CSRF 令牌。对所有非 GET/HEAD 的 `/api` 请求：

1. `Origin` 请求头必须存在且等于 `APP_ORIGIN`，否则返回 `403 ORIGIN_FORBIDDEN`。
2. 请求体只接受 `application/json`。

配合 `SameSite=Lax`，跨站页面无法带着 Cookie 发出写请求。实时通道握手同样校验 `Origin`。

### 6.5 限速

用 `@fastify/rate-limit`，计数存在进程内存（单实例足够）。客户端地址取自受信任代理传来的转发头，因此 `TRUST_PROXY` 必须配置正确。

| 接口 | 限制 |
|---|---|
| 登录 | 每个地址每分钟 10 次；另按登录名统计，15 分钟内失败 5 次后该登录名锁定 15 分钟 |
| 查看邀请、用邀请注册 | 每个地址每分钟 20 次 |
| 查看重置链接、用重置链接设密码 | 每个地址每分钟 20 次 |
| 其余接口 | 每个会话每分钟 600 次 |

超限返回 `429 RATE_LIMITED`。

## 7. 权限与项目范围

这是阶段 1 最重要的公共机制，后续每个阶段的每个接口都建立在它上面。

### 7.1 权限表

定义在 `packages/shared/src/permissions.ts`，前端用它决定显示哪些入口，服务端用它做最终判定。

| 权限键 | 管理员 | 普通用户 | 首次使用的阶段 |
|---|---|---|---|
| `users.manage`（调整角色、生成重置链接） | ✓ | ✗ | 1 |
| `invites.manage` | ✓ | ✗ | 1 |
| `diag.realtime` | ✓ | ✗ | 1 |
| `worksheets.manage`（建表、归档、配置工序列与看板列） | ✓ | ✗ | 2 |
| `data.import` / `data.export` | ✓ | ✗ | 5 / 6 |
| `storage.manage` | ✓ | ✗ | 6 |

查看和编辑任务内容对所有已登录用户开放，不需要权限键。代码里判断权限一律用权限键，不直接比较角色名。

### 7.2 路由的访问声明

每个 `/api` 路由必须在路由配置里显式声明访问级别，三选一：

- `public`：无需登录（仅登录、邀请查看与注册、重置查看与提交、健康检查）。
- `authenticated`：任何已登录用户。
- `{ permission: '<权限键>' }`：需要该权限。

一个全局钩子按声明执行鉴权；**没有声明的路由在应用启动时直接报错**，因此不可能因为忘写而出现未受保护的接口。有一项测试枚举全部已注册路由并断言 `public` 的集合恰好等于上面列出的那几个。

鉴权通过后，`request.auth` 提供 `{ userId, projectId, role, sessionId }`。`projectId` 来自该用户唯一的 membership，**从不取自请求参数或请求体**。

### 7.3 项目范围

1. 数据访问层的每个查询函数都以 `projectId` 为第一个必填参数，并把它写进 `WHERE`。不提供“按 ID 取任意项目对象”的函数。
2. 路径或请求体里的对象 ID 属于其他项目，或根本不存在，一律返回 `404 NOT_FOUND`，响应不区分这两种情况。
3. 实时订阅在订阅时校验该范围属于连接所在的项目（第 8.3 节）。
4. 测试夹具提供 `createTwoProjects()`，直接向数据库写入两个互不相干的项目及各自的管理员和普通用户（接口层不提供建项目的途径）。隔离测试的写法固定：用项目乙的会话，带项目甲的对象 ID 调用每一个带 ID 参数的接口，断言 404 且甲的数据未变。**后续阶段每新增一个带 ID 的接口，必须在同一个测试文件里加一条。**

## 8. 实时通道

方案与取舍见设计文档第 11.5 节。本节是可直接实现的协议与规则。

### 8.1 连接与握手

- 地址 `GET /api/realtime`，升级为 WebSocket。
- 升级前校验：`Origin` 等于 `APP_ORIGIN`；Cookie 对应有效会话。任一不满足则**拒绝升级**（返回 HTTP 403 或 401），不建立连接。
- 建立后服务端立即发送 `hello`，其中的 `connId` 是该连接的随机标识。
- 服务端每 25 秒发一次 `hb`；同时检查该连接的会话是否已过期，过期则以代码 4401 关闭。客户端 60 秒内未收到任何消息即认为连接已断，主动关闭并重连。
- 客户端重连采用退避：1、2、5、10、30 秒，之后保持 30 秒，每次加 0–1 秒随机抖动；页面从后台回到前台或网络恢复时立即重试。

关闭代码：`4401` 会话失效；`4403` 无权；`4400` 协议错误（消息无法解析或类型未知）。客户端收到 `4401` 后不再重连，跳转登录页。

### 8.2 消息

全部为 JSON 文本帧，字段 `t` 表示类型。事件编号与游标是十进制字符串（`bigint`）。类型与 Zod 定义放在 `packages/shared/src/realtime.ts`。

客户端发往服务端：

| `t` | 字段 | 说明 |
|---|---|---|
| `subscribe` | `scope: {type, id}`，`cursor?` | 订阅一个范围；带游标表示请求补发 |
| `unsubscribe` | `scope` | |
| `presence` | — | 阶段 2 使用；本阶段服务端收到后忽略 |

服务端发往客户端：

| `t` | 字段 | 说明 |
|---|---|---|
| `hello` | `connId`，`protocol: 1` | |
| `subscribed` | `scope`，`cursor` | 订阅成功；`cursor` 是该范围当前的最新编号，随后可能跟着补发的事件 |
| `event` | `id`，`scope`，`type`，`payload`，`actorUserId`，`at` | 一条实时事件 |
| `resync` | `scope`，`cursor` | 无法补发，客户端应整体刷新该范围，并把游标设为给出的值 |
| `error` | `code`，`message`，`scope?` | 如订阅被拒 |
| `hb` | — | 心跳 |

客户端**不通过实时通道写入任何业务数据**，所有修改走 HTTP 接口。

### 8.3 订阅范围

范围类型通过注册表登记，每种类型提供一个授权函数 `(auth, scopeId) => boolean`。阶段 1 登记两种：

| 类型 | `id` | 谁能订阅 | 承载的事件 |
|---|---|---|---|
| `project` | 项目 ID | 该项目的任何用户 | `user.updated` |
| `diag` | 项目 ID | 该项目中有 `diag.realtime` 权限的用户 | `diag.ping` |

订阅其他项目的范围、未登记的类型、或无权的范围，回复 `error`（`code: "FORBIDDEN"`），响应不区分“不存在”与“无权”。阶段 2 在同一注册表里登记 `worksheet` 与 `task`。

用户的角色被调整后，服务端重新校验该用户所有连接上的订阅，对已不满足授权的范围发送 `error` 并取消订阅。

### 8.4 写入与广播

所有会产生实时事件的修改都通过同一个事务封装 `withTx(auth, fn)` 完成：

1. `fn` 在事务内执行业务修改，并调用 `emit({scope, type, payload})` 登记事件。
2. 若登记了事件，封装在提交前先取得**按项目的事务级咨询锁**（`pg_advisory_xact_lock`，键由项目 ID 派生），再把事件插入 `realtime_events`。这保证同一项目内事件编号的顺序等于提交顺序。若不加锁，编号小的事务可能后提交，一个已拿到较大游标的客户端重连时会漏掉它。
3. 事务提交成功后，把带编号的事件交给事件总线分发。事务回滚则什么都不发。
4. 事件总线是一个接口（`publish(events)` / `subscribe(handler)`），阶段 1 只有进程内实现。将来多实例时换成基于发布订阅的实现，调用方不变。

发起者去重：HTTP 请求可带 `X-Connection-Id` 请求头（值为自己的 `connId`），写入事件的 `origin_conn_id`；分发时跳过该连接。发起者以接口返回值为准更新自己的界面。

事件载荷规则：只放对该范围所有订阅者都可见的内容。阶段 1 的两种事件：

| 类型 | 范围 | 载荷 | 触发 |
|---|---|---|---|
| `user.updated` | `project` | `{userId}` | 用户注册、改显示名、角色被调整。客户端收到后重新请求用户列表；若是自己，重新请求 `/api/auth/me` |
| `diag.ping` | `diag` | `{message, sentAt}` | 诊断页发送测试事件 |

### 8.5 订阅、补发与整体刷新

处理一条 `subscribe` 的顺序是固定的，用来消除“补发查询与实时分发之间漏事件”的竞态：

1. 校验授权。
2. 先把连接登记为该范围的订阅者，但进入**缓冲状态**：此时分发来的事件暂存，不发送。
3. 读取该范围当前最大事件编号 `head`（没有事件则取该项目的 `realtime_pruned_through`，再没有则为 `0`）。
4. 若请求没带游标：发送 `subscribed {cursor: head}`。
5. 若带了游标 `c`：
   - `c` 小于该项目的 `realtime_pruned_through`，或该范围内编号大于 `c` 的事件超过 `REALTIME_REPLAY_LIMIT` 条：发送 `subscribed`，再发送 `resync {cursor: head}`。
   - 否则：发送 `subscribed`，再按编号升序发送全部编号大于 `c` 的事件。
6. 退出缓冲状态，把暂存的事件按编号升序发出，跳过编号不大于已发送最大编号的。

客户端规则：

- 对每个范围记住最后收到的事件编号作为游标。收到编号不大于游标的事件直接丢弃。
- **先订阅、后读数据。** 首次进入一个页面时，先发 `subscribe`（不带游标）并等到 `subscribed`，再通过 HTTP 读取该范围的数据。读取期间到达的事件在读取完成后再应用。反过来做会漏掉两步之间发生的变更。
- 重连后对每个仍需要的范围重新 `subscribe` 并带上游标。
- 收到 `resync`：丢弃该范围的本地缓存，通过 HTTP 重新读取，游标设为消息里给出的值。

### 8.6 会话失效时断开

连接登记表按 `sessionId` 索引。凡是删除会话的事务，提交后调用 `realtime.closeSessions(sessionIds)`，以代码 `4401` 关闭这些会话上的全部连接。涉及的操作见第 6.3 节。

### 8.7 清理

pg-boss 定时作业，每小时一次：对每个项目删除 `created_at` 早于 `REALTIME_RETENTION_HOURS` 的事件，并在同一事务里把被删除的最大编号写入 `projects.realtime_pruned_through`（只增不减）。

### 8.8 降级

实时通道不可用时其他功能照常工作。界面顶部显示“连接中断，正在重连”，重连成功后消失。

## 9. HTTP 接口

前缀 `/api`。请求与响应均为 JSON。成功返回 2xx 与数据本身；失败返回：

```json
{ "error": { "code": "VALIDATION_FAILED", "message": "显示名已被使用", "fields": { "displayName": "已被使用" } } }
```

`message` 是可直接展示给用户的中文。错误码定义在 `packages/shared`：

| HTTP | code | 含义 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | 输入不合规则；`fields` 给出逐字段原因 |
| 401 | `UNAUTHENTICATED` | 未登录或会话失效 |
| 401 | `INVALID_CREDENTIALS` | 登录名或密码错误 |
| 403 | `FORBIDDEN` | 已登录但无权限 |
| 403 | `ORIGIN_FORBIDDEN` | 来源校验失败 |
| 404 | `NOT_FOUND` | 对象不存在或不属于本项目 |
| 409 | `CONFLICT` | 违反唯一性或不变量，如登录名已存在、不能降级最后一个管理员 |
| 410 | `TOKEN_INVALID` | 邀请或重置链接无效、过期、已用完或已作废（不区分原因） |
| 429 | `RATE_LIMITED` | |
| 500 | `INTERNAL` | 不向客户端暴露内部细节 |

| 方法与路径 | 访问 | 请求 | 响应与说明 |
|---|---|---|---|
| `GET /health` | public | — | `{status:"ok"}`，只表示进程存活 |
| `GET /health/ready` | public | — | 数据库可查询时 200，否则 503 |

邀请链接形如 `${APP_ORIGIN}/invite/<令牌>`，重置链接形如 `${APP_ORIGIN}/reset/<令牌>`。两者由前端路由渲染页面，页面再调用上面的接口。

- **登录**：登录名、密码。错误提示不区分登录名不存在与密码错误。被限速时提示稍后再试。

- **用户与邀请**：
  - 用户列表：显示名、登录名、角色、加入时间。可调整角色；为他人生成重置链接前弹出确认，写明“对方当前密码将立即失效并被登出所有设备”。生成后在弹窗里显示链接与复制按钮，并说明链接只显示这一次。
  - 邀请列表：角色、状态（有效 / 已用完 / 已过期 / 已作废）、已用次数、到期时间、创建人。创建邀请的表单可选角色、有效期、次数；创建后同样只显示一次链接。可作废。
  - 列表订阅 `project` 范围，收到 `user.updated` 时刷新。
- **实时通道诊断**（验收工具，后续阶段保留作排障用）：显示连接状态、`connId`、`diag` 范围的当前游标；按时间倒序的事件日志（编号、类型、内容、发送人、是否补发得到）；“发送测试事件”输入框与按钮；“模拟断线”按钮（客户端主动关闭连接并暂停自动重连）与“恢复连接”按钮；收到 `resync` 时在日志里显示一条明显的记录。

### 10.3 实现约定

- 服务端状态用 TanStack Query 管理；查询键集中定义在 `apps/web/src/api/keys.ts`。
- 请求封装统一处理：自动带 `X-Connection-Id`；`401 UNAUTHENTICATED` 时清空缓存并跳登录页；把错误体转换成带 `code` 与 `fields` 的异常。
- 表单用 react-hook-form，校验直接复用 `packages/shared` 的 Zod 定义。
- 实时客户端是一个与 React 无关的类（连接、心跳超时、退避重连、订阅表、游标、事件分发），另提供 `useRealtimeScope(scope, handlers)` 钩子。它要能在 Vitest 里用假的 WebSocket 单独测试。
- 所有用户输入内容以文本方式渲染，不使用 `dangerouslySetInnerHTML`。

## 11. 交付：CI、镜像与部署

### 11.1 CI

`.github/workflows/ci.yml`，在推送和拉取请求时运行，Node 24，带 `postgres:18` 服务容器：

1. 安装依赖（`pnpm install --frozen-lockfile`）。
2. `pnpm check`。
3. `pnpm test`。
4. `pnpm build`。
5. 安装 Playwright 的 Chromium 后执行 `pnpm e2e`；失败时上传跟踪文件。
6. 仅在 `main` 分支且以上全部通过时：构建镜像并推送到 `ghcr.io/1zero224/nameless-worksheet`，标签为提交 SHA 与 `latest`。使用工作流自带的 `GITHUB_TOKEN`，并声明 `permissions: packages: write`。

不做“推送即自动上线”。部署由人或代理手动执行第 11.3 节的脚本。

### 11.2 镜像与 Compose

`Dockerfile` 多阶段构建：构建阶段安装全部依赖并构建三个包；运行阶段基于 `node:24-bookworm-slim`，只含生产依赖、服务端产物和前端静态文件，以非 root 用户运行，带 `HEALTHCHECK`（请求 `/api/health`）。

`deploy/compose.yaml`（用于当前 VPS）：

| 服务 | 要点 |
|---|---|
| `db` | `postgres:18`；数据目录绑定到 `./pgdata`（**挂载路径以 `postgres:18` 镜像文档为准**，18 起的数据目录布局与旧版本不同 【未验证】）；不发布端口；内存上限 512 MB，`shared_buffers=128MB`；带健康检查 |
| `app` | 镜像标签由 `.env` 中的 `APP_IMAGE_TAG` 指定；等待 `db` 健康后启动；发布 `172.19.0.1:18610:3000`；内存上限 512 MB；`restart: unless-stopped` |

两个服务在 Compose 自建的内部网络上互通。`deploy/compose.caddy.yaml` 是叠加文件，增加一个自带的 Caddy 服务并改为发布 80/443，仅供将来换到干净机器时使用，当前不启用。

`deploy/.env.example` 列出全部变量并入库；真实的 `.env` 只存在于 VPS 的部署目录，权限 `600`，不入库。数据库密码在首次部署时于 VPS 上用 `openssl rand` 生成并直接写入 `.env`，不出现在聊天记录、日志或仓库中。

### 11.3 部署步骤

`deploy/deploy.sh <镜像标签>` 在开发机上运行，通过 SSH 完成以下事情：

1. 确认部署目录存在；把 `compose.yaml` 同步过去。
2. 检查系统盘剩余空间，低于 2 GB 时中止并报告（镜像存放在系统盘）。
3. 更新 `.env` 中的 `APP_IMAGE_TAG`，`docker compose pull app`。
4. `docker compose run --rm app node dist/cli.js migrate`。
5. `docker compose up -d`，等待健康检查通过；失败则把 `APP_IMAGE_TAG` 改回上一个值并重新 `up -d`，然后报告失败。
6. 只清理本项目的旧镜像（按镜像名过滤，保留最近 3 个），不执行全局的 `docker system prune`。

首次部署另有三件一次性的事：

- **【需用户】让 VPS 能拉取私有镜像。** 在 GitHub 生成只有 `read:packages` 权限的访问令牌，在 VPS 上执行 `docker login ghcr.io -u 1zero224` 并粘贴令牌。代理不接触该令牌。
- 创建 `/srv/storage/nameless-worksheet/`，生成 `.env`。
- 配置 Caddy（下一节），然后执行初始化命令：`docker compose run --rm app node dist/cli.js init --project "无名字幕组" --admin <登录名> --display-name <显示名>`。**【需用户】** 登录名与显示名由用户提供；命令输出的重置链接交给用户，由用户在浏览器里设置密码。

### 11.4 在 VPS 上的操作边界

用户已授权代理通过 SSH 自行配置，但这台机器上有其他正在运行的服务。代理只能：

- 读写 `/srv/storage/nameless-worksheet/` 之下的内容；
- 操作本项目 Compose 管理的容器、网络与镜像；
- 向 `/opt/gotify/Caddyfile` **追加**本项目的站点块，并热重载 `gotify-caddy`。

不得：重启、重建或停止任何其他容器与进程（包括 `gotify-caddy`）；修改 `/opt/gotify/compose.yaml`；修改 Caddyfile 中已有的站点块；改动 Docker 守护进程配置或根目录；改防火墙与系统设置；执行全局清理命令。遇到需要越界才能继续的情况，停下并报告。

### 11.5 配置 Caddy

站点块的来源是仓库里的 `deploy/Caddyfile.snippet`，写法与机器上其他站点保持一致：

```caddyfile
worksheet.45.207.215.102.sslip.io {
    encode zstd gzip
    header {
        -Server
        Strict-Transport-Security "max-age=31536000"
        X-Content-Type-Options "nosniff"
        X-Frame-Options "DENY"
        Referrer-Policy "no-referrer"
    }
    request_body {
        max_size 1MB
    }
    reverse_proxy 172.19.0.1:18610 {
        header_up X-Real-IP {remote_host}
        flush_interval -1
    }
}
```

Caddy 的 `reverse_proxy` 会自动转发 WebSocket 升级，不需要额外配置。`max_size 1MB` 对阶段 1 足够（文件上传在阶段 4 直传 R2，不经过本服务）。

操作顺序：

1. 确认应用已在 `172.19.0.1:18610` 上响应健康检查。
2. 备份：`cp -p /opt/gotify/Caddyfile /opt/gotify/Caddyfile.bak-<日期时间>`。
3. 在 VPS 上生成候选文件（现有内容 + 站点块），用 `docker cp` 放进容器的 `/tmp`，执行 `docker exec gotify-caddy caddy validate --adapter caddyfile --config /tmp/<候选文件>`。校验不过就停下，不改动真实文件。
4. 用 `cat deploy片段 >> /opt/gotify/Caddyfile` **原地追加**。**不要用会替换文件的方式写入（`sed -i`、编辑器保存、`mv` 覆盖等）**：该文件是单文件绑定挂载，文件被替换后容器里看到的仍是旧文件。
5. 确认容器内看到了新内容（`docker exec gotify-caddy grep worksheet /etc/caddy/Caddyfile`），然后热重载：`docker exec gotify-caddy caddy reload --adapter caddyfile --config /etc/caddy/Caddyfile`。
6. 验证：新站点的 `https://…/api/health` 返回 200；**同时抽查一个原有站点仍然正常**（例如 `https://45.207.215.102.sslip.io` 能返回响应）。原有站点异常则立即用备份内容原地覆盖回去（`cat 备份 > /opt/gotify/Caddyfile`）并再次重载，然后报告。

将来买到域名：改站点块里的域名与 `.env` 里的 `APP_ORIGIN` 两处即可，Cookie 会因域名变化而全部失效，用户需重新登录。

| 邀请与重置链接只显示一次 | 丢失后只能重新生成 | 按反馈 |
| 数据库备份 | 阶段 1 不做。**在阶段 6 备份就绪之前，不要让用户往系统里填真实的、不可丢失的数据** | 阶段 6 |
| 会话失效时断开实时连接 | 用户说“不做停用后被断开”，本文理解为只去掉与停用相关的部分，保留登出、改密码、重置后的断开；这是 AI 的理解 | 用户审阅本文时确认 |

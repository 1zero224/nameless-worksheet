# 采用 Teable MIT Canvas 表格引擎、作品大标题聚合与多级直通附件槽位

阶段 2 交付后，经真实使用与对比评测，发现原纯 DOM 手写表格外壳与平铺看板存在三处产品形态偏移：

1. **视觉与交互质感偏管理后台**：手写 Tailwind 灰框与高饱和多色胶囊缺乏统一设计规范，表格手感、侧边栏与视图切换明显弱于 Teable / 飞书多维表格；
2. **「作品—任务」表现违背原工作簿直觉**：将「作品」作为普通列在每个分段行里重复填写，既占列宽又看不出分块；在看板中，一部长视频拆成多段后裂成大量碎片卡刷屏；
3. **工序与文件割裂**：若所有文件仅集中在最右统一「文件」列与大抽屉中，下游无法在【时轴】【翻译】等工序格直接拿走最新交付，整部作品的共用原片也缺少天然挂载点。

用户同时明确了两条不可妥协的业务底线：**不能接受无同名文件自动版本堆叠**，**不能接受不支持同一任务并行出现在多个看板列**，因此排除直接采用原版 Teable / NocoDB / Grist；又因 Teable 全仓达 8,361 个文件且需 4 GB+ 运行 / 8–16 GB 编译内存，排除深度 Fork 魔改其全栈应用。

## 最终决策（经人类负责人明确批准）

1. **按 MIT 协议抽离 Teable Canvas 表格核心**：在保留本项目轻量后端（Node + Fastify + PostgreSQL + 实时协同）的前提下，仅将 `research/teable/packages/sdk/src/components/grid/`（91 个文件，隶属 `@teable/sdk` 的 **MIT 许可**）精简去耦引入至 `apps/web/src/vendor/teable-grid/`，保留原始 MIT `LICENSE` 与版权声明，绝不引入 Teable 名称、Logo 等受保护品牌资产，绝不拷贝 `apps/` 下 AGPL 代码。
2. **统一 Teable 极简视觉体系与动效底座**：采用正版 `shadcn/ui` 中性灰阶与半透明细边框 Token（`rgba(0,0,0,0.08)`），搭配精确锁版本的 `tw-animate-css`、`motion`、`sonner`，重构极简左侧栏与工作表顶部「表格视图 / 看板视图」标签栏。
3. **工作表「作品大标题横幅」+ 看板「列内按作品聚合卡」**：
   - 工作表中归属同一作品的任务聚合在跨整行可折叠大标题横幅下（基于 `teable-grid` 原生 `LinearRowType.Group`），无作品的独立任务直接平铺，默认隐藏冗余「作品」列；
   - 看板保留跨表并行工序多列显示与原子抢认领，但将同列内同作品的多条分段合并为默认折叠的「作品聚合卡」（点击平滑展开分段），并支持看板列竖向折叠与卡片视觉去噪。
4. **阶段 3 统一四级附件挂载模型**：`artifacts` 表通过可空归属字段覆盖**项目参考资料 / 作品大标题级（整片原片、字体包、合稿成品）/ 任务行级（独立任务原片与成品）/ 工序格级（本工序空轴、翻译稿、校对稿，格内角标一键下载最新版）**；删除工序列时工序级附件自动降级为任务级，删除作品前须显式保护确认。

## 考虑过的方案

- **直接部署原版 Teable（不魔改）**：UI 极佳但无法满足同名文件自动版本堆叠、10 GiB R2 分片续传、作品大标题直接挂原片与跨表并行工序多列看板，被用户明确否决。
- **深度 Fork 魔改 Teable / Baserow 源码**：全栈耦合极深（5,500–8,300+ 文件）、VPS 内存不足、升级与 AI 迭代成本过高，排除。
- **更换 Mantine / Ant Design 等通用中后台框架**：仍为普通 DOM 表格形态，视觉与多维表格手感不及 Teable，排除。

## 后果

- `AGENTS.md` 第 1 条同步补充对 `apps/web/src/vendor/teable-grid/` 的 MIT 抽离例外说明（按防篡改规则在提交说明中显式标注原因）。
- 工作表主渲染切换为 Canvas 网格后，需为工序格维护自定义 `stageCellRenderer.ts`，并在 E2E 中确保中文 IME、并发冲突条、在线状态焦点框与 `390×844` 窄屏兜底继续全量自动化验收。
- 阶段 3 启动时按四级归属建表，实验分支中先只预留作品大标题与工序格的附件槽位接口，不提前改动后端与数据库。
